# Fraud Arena 1v1

Status: proposal, 2026-11-21. Replaces the v0 multiplayer game (design doc 20 §8 in Runmere) as the first benchmark.

## Why

The v0 game ran four defenders and up to four rings at once, as Claude Code and Codex sessions in a shared EC2
sandbox. Defenders deployed bundles of rules and ML models and wrote weekly loss reviews. A Grayson token broker
sat in between, and the ranking was Nash averaging over teams. It needed unmerged engine PRs (#31, #35, #41, #42),
and the 2026-11-16 review found that players could read each other's files and see each other's model credentials.

1v1 keeps the core question: can an agent defend an institution against an agent that adapts? It drops everything
else.

## The game

**One defender at one bank against one attacker (a fraud ring).** Everyone else in the world, including the
legitimate customers who supply the look-alikes, follows the world's built-in behavior.

- **World:** Runmere `main`, `spec/examples/payments-ato-mini.world.yaml`, episode `auth_vs_adversary`: account
  takeover against `demo_bank`, 180-day warm-up, 30-day horizon, one victim per episode. The engine already exposes
  both roles in one episode, with built-in policies for each. No engine PRs are needed.
- **Rounds.** A match is `R` rounds (default 8). A round is a batch of `N` episodes (default 50) on fixed seeds from
  the test split. Each round slot uses the same seeds in every match, so every pairing faces the same victims.
- **Policies, not per-transaction calls.** During a round, the harness answers every gate from each player's current
  policy. Between rounds, each player gets one turn to inspect what it can see and submit a new policy. A match is
  about `2R` agent turns, not thousands of per-decision model calls.

### Defender

- **Decision:** `card_auth` (approve, decline, step_up) on every card purchase in the episode. Default: approve.
- **Policy:** an ordered rule list; the first matching rule decides. A rule is a conjunction of conditions on the
  gate's observation (`auth_view`): `amount`, `ecommerce`, `new_device`, `txn_count_7d`, `contact_changed_7d`,
  `failed_logins_1d`, `ip_risk`. Rules are data (JSON), evaluated by the harness. No player code runs in the engine.
- **Sees:** the bank's observed tables (`CARD_TXN`, `LOGIN_EVT`) for its rounds so far, its own decisions, and
  confirmed fraud only once it is knowable (the world's `knowable_after` delays). Never the cause, scenario or
  labels before then.

### Attacker

- **Decisions:** `ato_route` (cheap or stealth), `ato_takeover` (change_email or keep_contact), `ato_cash_out`
  (small, medium, large, blend, drain, stop) and `ato_after_decline` (retry_lower or wait).
- **Policy:** a plan of the same shape: a default per decision, plus optional conditions on that decision's own
  observation (`victim_age`; `failed_logins_7d`; `hijacked`, `approved_1d`, `refused_1d`, `days_in`; `amount`).
- **Sees:** only its own attempts and their outcomes (approved, declined, stepped up) and its gains. Never the bank's
  rules or tables.
- **Writes no fraud content.** It picks from the world's menu. This keeps models willing to play and the benchmark
  from being a fraud tutorial.

### Scoring

- **Reference run:** the same seeds with both built-in policies (the bank's rules, the scripted fraudster).
- **Defender score:** its `auth_reward` (fraud losses and friction on good customers) minus the reference run's.
- **Attacker score:** its `adversary_reward` (gains, minus the stealth route's costs) minus the reference run's.
- **Table:** every model plays both roles against every model, self-play included, plus baseline players:
  - **defenders:** the built-in rules and approve-all
  - **attackers:** the scripted fraudster and always-drain

  Report each model's mean and worst-case score in each role, with bootstrap intervals over seeds. Also report the
  score after each round, which shows adaptation over the match.

## Harness

Both roles use the same agent: **mini-SWE-agent**, with one shell command per step, so it works with any model.

- **One Docker container per player per match.** It holds only that player's view (as SQLite files and JSON) and an
  `arena` CLI:

  | Command | Who | What it does |
  |---|---|---|
  | `arena status` | Both | The current round, scores so far, and the policy format |
  | `arena query "<SQL>"` | Defender | Runs a query on the bank's tables |
  | `arena attempts` | Attacker | Lists its own attempts and their outcomes |
  | `arena policy show` | Both | Prints the current policy |
  | `arena policy set <file>` | Both | Validates a new policy and stores it |
  | `arena submit` | Both | Ends the turn |

  The CLI talks to the match runner over a per-container socket. A player can't reach the other player, the
  engine or the truth tables.
- **Same prompt template for both roles**, apart from the role brief and the command list.
- **Per-turn limits:** a step cap (default 20 commands), a token cap and a wall-clock cap. An invalid or missing
  policy keeps the previous one, and the failure is recorded.
- **Models:** through OpenRouter (an OpenAI-compatible API), pinned by exact model ID, at temperature 0 where the
  model allows it. Every step, command, output, token count and cost is logged per turn.

## Explicitly out of v1

- several institutions or rings
- P2P scams and mules
- ML-model bundles
- manual review queues
- a Grayson tool
- coding-agent players (Claude Code, Codex)

Each can come back as its own track once the 1v1 table is stable.

## Plan

1. **Runner and CLI:** a match runner on Runmere's Python bindings (`episodes("auth_vs_adversary")`,
   `act` / `act_builtin`), the policy evaluators, the per-player views, and the CLI in a container.
2. **Smoke match:** baselines only (no models). Check that the reference run reproduces the built-in totals and
   that scores are zero.
3. **Cheap-model pilot:** 2–3 inexpensive OpenRouter models, short matches (R=4, N=20), both roles. Check for
   invalid policies, cost per match, and whether either side adapts at all.
4. **Full table:** a wider model set, R=8, N=50, three seed sets.

## Open questions

- **Is account takeover alone too narrow?** `p2p_30d` (scams) could be a second duel once it has an adversary role.
- **Should defenders see aggregate friction feedback each round** (complaints from declined good customers), or
  only through delayed labels?
- **Is the round count long enough** for the attacker to probe, and the defender to respond, more than once?
